**3. Why is the app slow?**

I doubt it's mostly the file system. On each refresh the app checks every meeting file's size and modification date, but it only re-reads files that changed. That refresh runs every time you switch back to the app. On a local disk with a few hundred meetings it takes a few milliseconds.

There's one exception. If the workspace is in iCloud Drive or on a network share, listing and checking files can take much longer, and it happens on every switch back.

The more likely causes are in how I built the in-memory side:

- **Debug builds:** `swift run` makes a debug build, and SwiftUI apps run noticeably slower in debug. The `.app` from `scripts/build-app.sh` is a release build.
- **Too much redrawing:** all the meetings are held in a single list. Each keystroke in a note changes that list, so the sidebar counts, the whole meeting list and the calendar are all recalculated, re-sorted and redrawn.
- **Slow lookups:** finding a meeting or a note means searching from the start each time, and that happens many times per redraw. Working out first names checks every person for every name shown. The cost grows quickly with more meetings.

What the standard macOS approaches would offer:

- **Keep the data in memory, but organise it better.** The app already holds everything in memory, so the fix is to:
  - look meetings up directly by ID instead of searching;
  - work out the sorted and grouped list only when meetings change;
  - make typing in a note redraw only that note.

  This is probably where most of the gain is.
- **Coordinate with other apps instead of rescanning.** Apple's mechanisms for this are file coordination (`NSFileCoordinator` and `NSFilePresenter`, which document-based apps use) and FSEvents. They tell the app which files changed, so it wouldn't rescan on every switch back. Coordinated writes are also the recommended way to avoid clashing with iCloud Drive or sync tools, and writes would stay atomic.
- **Write in the background.** A background queue could save to disk so the interface never waits on it, combining repeated saves of the same file. Anything pending would be flushed reliably when you switch away or quit; on quit the app would wait until saves finish.
- **A disposable index cache.** This is what Bibliotheca does in `~/Library/Caches`. It would only matter for launch speed once you have thousands of meetings.
- **Core Data or SwiftData:** this is Apple's heavyweight answer, but I'd advise against it. It makes a database the real copy of your data and the folder a mirror, which goes against the plain-folder design and Git or Syncthing syncing.

My recommendation:
1. Measure, then reorganise the in-memory data.
2. Replace the rescan on every switch back with change notifications and coordinated writes. This matters especially if you use iCloud Drive.
3. Leave the background writer and the index cache until a workspace actually needs them.

To help me target the fix:
- **What feels slow?** For example typing in a note, selecting a meeting, switching to the calendar, launching, or coming back to the app.
- **Which build are you running?** The debug build from `swift run`, or the `.app` from `scripts/build-app.sh`?
- **Where is your workspace, and how big is it?** Is it local, in iCloud Drive or synced some other way, and roughly how many meetings does it have?
